<instructions>
Work through three steps:

Step 1 — Understand the video:
- Who made this and what's their style?
- What's the core promise — what can the viewer DO after watching?
- What makes THIS video different from 1000 others on the same topic?
- What specific data can be extracted (count items: ingredients, steps, spots, code snippets, etc.)?

Step 2 — Classify the content:
Pick 1-2 content tags (most specific first) and 0-2 modifiers.
Content tags: learning, tech, fitness, food, music, travel, review, project, language, science
Modifiers: narrative (strong storytelling), finance (specific costs/budgets)

Step 3 — Design the output:
Create 4-6 interactive tabs using the component toolkit below.
- First tab: delivers the video's primary value immediately (not an overview)
- Every tab needs a "goal" explaining what the user DOES with it
- Use at least 2 interactive components (action, learning, exploration, or media)
- Maximum 1 display component (verdict, budget)
- Tab labels should include specific numbers when known (e.g., "🛒 14 Ingredients")
- Match components to user actions, not data shape
</instructions>

<outbound_links_instructions>
For every tab you emit, include an `outboundLinks` map: a dict whose keys are the IDs of OTHER tabs you ALSO planned (never reference an id that isn't in your tabs array), and whose values are short 2–5 word navigation labels.

The label is a call-to-action — what the viewer should DO at the target tab ("Learn the concepts", "Check ingredients", "Try the code"). Write each label in the SAME LANGUAGE as the rest of your output (the video's language). For an English video output English labels; for a Hebrew video output Hebrew labels; etc.

These labels are pipeline output — they flow through the translation walker, so the English-primary surface gets English labels even when you wrote Hebrew here, and the original-language toggle keeps your source-language labels intact. Hardcoded English here would defeat that flow.

Only include outbound entries that make semantic sense (overview→content tab, content tab→test, etc.). Omit `outboundLinks` entirely on a tab that has no good outbound suggestions — the assembler will fall back to using the target tab's own label.
</outbound_links_instructions>

<domain_requirements>
Domain-required components — if the domain is present in contentTags, these components MUST appear. The assembler does NOT enforce per-domain required components; missing them is a silent planning bug that ships a malformed tab layout, so treat this section as a hard contract on your side:

- food: MUST include `checklist` (ingredients) + `step_player` (recipe steps)
- project: MUST include `checklist` (materials) + `step_player` (build steps)
- review: MUST include `comparison` (folds verdict score + recommendation into the same tab)
- fitness: MUST include `exercise_tracker`
- travel: MUST include `spot_explorer` (itinerary)
- music: MUST include `lyrics_player` when lyrics are available in the transcript
- language: MUST include `spot_explorer` (phrases) AND `flash_deck` (vocabulary) when the
  extraction has at least 3 vocabulary items with definition shape
- science: MUST include `flash_deck` (concepts) when extraction has at least 3 concept-definition
  pairs. Add `moment_track` if the video has demonstrations.
- learning: MUST include `moment_track` for chapter navigation when transcript has timestamps.
- tech (with has_code=true): MUST include `code_explorer`.
- ALL domains: the assembler emits an overview hero at the top — DO NOT plan a separate
  "overview" tab. The first tab you design IS the first user-facing content tab.

flash_deck restrictions:
- flash_deck is for memorization of concept-definition pairs. Each card front must be a real
  term or concept; the back is the definition.
- Pick flash_deck when extraction has 3+ items shaped {name|term, definition} — even if the
  domain isn't "learning". Concepts in science, tech terms, language vocabulary all qualify.
- Maximum 1 flash_deck per video.
- Never use flash_deck for: tips, features, analysis, trivia, narrative moments. Those go to
  info_grid (browse) or moment_track (jump).

quiz / scenario restrictions:
- quiz and scenario tabs are only for learning and tech domains.
- Both pull from enrichment.* — they're added when extraction supports a knowledge check.
</domain_requirements>

<routing_matrix>

Detect intent from video title and content structure:
  - "How to..." / sequential steps / tutorial → DO
  - "Explained" / "What is" / definitions / theory → LEARN
  - "vs" / "Review" / "Best" / pros-cons → DECIDE

┌──────────┬──────────────────────────┬────────────────────────────┬─────────────────────────┐

├──────────┼──────────────────────────┼────────────────────────────┼─────────────────────────┤
│ food     │ step_player + checklist  │ info_grid + flash_deck     │ spot_explorer (methods)  │
│ project  │ step_player + checklist  │ info_grid (techniques)     │ comparison (skill lvls)  │
│ tech     │ code_explorer (guided)   │ flash_deck + quiz          │ comparison + verdict     │
│ review   │ —                        │ info_grid (specs)          │ comparison + verdict     │
│ travel   │ spot_explorer + budget   │ info_grid (culture/tips)   │ comparison (routes)      │
│ fitness  │ exercise_tracker         │ flash_deck (form cues)     │ comparison (programs)    │

│ learning │ code_explorer / scenario │ flash_deck + quiz          │ comparison               │
│ language │ step_player (drills)    │ flash_deck (vocabulary)    │ spot_explorer (phrases)  │

└──────────┴──────────────────────────┴────────────────────────────┴─────────────────────────┘

Every video has ONE primary intent. Pick the column, use those components as required tabs.
The first content tab YOU design is what users see first — make it the primary value tab
(the action / the comparison / the timeline), not a meta summary. The overview hero is
emitted automatically by the page chrome above your tabs.
</routing_matrix>

<format_routing>
When content_traits are available, use them to override default component choices:
- has_drills=true → prefer step_player, spot_explorer. AVOID flash_deck (drills are practice, not memorization). Exception: language domain vocabulary tab may use flash_deck.
- has_narrative=true → prefer moment_track with endSeconds on highlight moments. AVOID flash_deck (stories aren't flashcard material).
- is_list=true → prefer spot_explorer for browsable items. AVOID step_player (lists aren't sequential).
- has_code=true → MUST include code_explorer tab.
- has_comparison=true → MUST include comparison tab.
- has_visual_demo=true → prefer moment_track with endSeconds on the demo spans.
- is_opinionated=true → prefer info_grid for arguments/points. AVOID quiz (opinions aren't testable).
- has_steps=true → prefer step_player for sequential instructions.
</format_routing>

<tab_goal_guidance>
tab.goal is shown to the user as an intro paragraph. Write it as a friendly, specific 1-sentence description — NOT developer documentation.

Bad: "Browse all egg cooking methods with technique notes"
Good: "59 ways to cook an egg. Tap any method to see temps, times, and Amiel's take."

Bad: "Review key woodworking techniques used at each level"
Good: "John uses different techniques at each level. Here's what you need for your build."

Bad: "Copy starter code patterns for browser and Node.js"
Good: "Grab these and paste into your editor. Each builds on the last."

code_explorer explanations should feel like pair-programming. "Let's build the counter function" not "Counter function implementation."
flash_deck front must be a real term or concept name. Never a category label like "chef_tip" or "pro_tip".
</tab_goal_guidance>

<extraction_caps>
More items ≠ more value. Long videos must NOT produce overwhelming lists. The user can scan ~10 things,
not 50. When planning tabs, cap the user-facing item count to these per-component maximums:

- comparison: at most 10 rows. If you have more candidates, pick the 10 most decision-relevant.
- moment_track (timeline / key moments): at most 20 items. Pick chapter jumps + the most replay-worthy spans.
- info_grid: at most 20 items. Group or section if you have more.
- flash_deck: at most 15 cards. Pick the 15 most-memorize-worthy terms.
- spot_explorer: at most 25 items.
- step_player: at most 25 steps (a recipe with 30 steps means group sub-steps).
- checklist: at most 30 items.

If the source content has more, surface the cap explicitly in tab.goal (e.g. "The 10 most important
comparisons from this 80-minute discussion"). NEVER produce a tab with 40+ items.
</extraction_caps>

<comparison_routing>
Comparison is for SIDE-BY-SIDE DECISIONS, not glossaries. Use it ONLY when ALL of these
conditions are met:
- The video explicitly weighs Option A against Option B on the SAME criteria.
- You have at least 3 comparison rows (features being weighed).
- Each row has substance on BOTH sides — not "A is X, B is unspecified".
- A user can DECIDE between A and B after reading the table.

The assembler drops comparison rows where one side is empty and drops the tab entirely if
no real pairs survive. Hitting the 3-row minimum is YOUR responsibility — the assembler
will ship a 1-row comparison if that's all you give it, and a 1-row table is a bad UX.

NEVER use comparison for:
- Term-and-definition lists (use info_grid for browsable lookup, flash_deck for memorization).
- "Here are 29 concepts" — that's a glossary, not a comparison.
- Pros without a counterpart (use info_grid).
- Reviews where only one product is examined — fold the verdict into overview meta instead.

If the video introduces many concepts WITHOUT explicitly weighing them against alternatives,
the right component is info_grid (browsable cards) or flash_deck (memorization). Reserve
comparison for moments where the speaker explicitly says "X is better than Y because…".
</comparison_routing>

<density_gates>
Target density per component — plan within these so the tab feels substantial. The assembler
ENFORCES a few of these (marked ✓); the rest are advisory and rely on you to plan correctly,
because a 1-item info_grid is technically a valid tab but a bad UX.

- info_grid: 3-20 items, each value ≤ 120 chars (≈20 words). Long paragraphs collapse
  into a wall of text — split into multiple short cells OR move to spot_explorer.
  ✓ enforced: items normalized (key + value both required, empty items dropped).
- comparison: ≥3 rows with both sides filled.
  ✓ enforced: single-side rows dropped; tab returned only if any real pair survives.
- flash_deck: 3-15 cards, front ≤40 chars, back ≤180.
- spot_explorer: 2-25 items.  ✓ enforced: minimum 2 items via `_MIN_SPOTS`.
- step_player: 3-25 steps.
- moment_track: 3-20 items.
- quiz: 2-8 questions.
- exercise_tracker: 2-25 exercises.
- checklist: 3-30 items.

If your extraction has fewer items than the target, route the data to a different
component or fold it into overview/info_grid via the fallback layer.
</density_gates>

<frame_intelligence>
Components are frame-aware. When you pick step_player, moment_track, code_explorer, or
exercise_tracker — AND the items carry a timestamp — the assembler attaches the nearest
vision-LLM frame caption, OCR text, and educational rationale automatically. This is
where the transcript and the on-screen frames fuse into "video-to-action".

To maximize frame evidence:
- Set `timestamp` (seconds) on every step_player step.
- Use `seconds` AND `endSeconds` on moment_track items for replayable highlights.
- Set `timestamp` on each code_explorer snippet.
- Prefer moment_track over a static info_grid when the video has rich visual demonstrations.

Standalone gallery is auto-appended ONLY when ≥10 vision captions are high quality — you
don't need to plan a gallery tab.
</frame_intelligence>

<rules>
- contentTags: 1-3, most specific first. Always include "learning" alongside domain tags when educational content is present.
- primaryTag: the dominant domain (must be in contentTags)
- confidence: 0.0-1.0
- tabs: 4-6 tabs, at least 2 using action/learning/exploration/media components
- maximum 1 display tab (verdict, budget)
- Every contentTag must have at least one tab using its domain data
- dataSource must reference a domain in this video's contentTags. NEVER use "learning.timestamps" for a food video or "travel.itinerary" for a tech video. Each dataSource prefix must match one of the contentTags or modifiers you assigned.
- dataSource must be from the valid datasources listed in the component toolkit
- component must be one of the 16 registered component names
- If unsure about content type, use ["learning"] with confidence below 0.6
- Tab IDs must be unique snake_case

CRITICAL — Ground tabs in the actual transcript:
- Only design tabs for data the transcript ACTUALLY contains. If you counted 0 items in itemCounts for a category, do NOT assign a tab that needs that data.
- flash_deck requires specific terms/concepts the viewer would memorize. If the transcript is conversational with no clear definitions, skip flash_deck.
- step_player requires sequential numbered steps. If the video is a discussion or review, don't force steps.
- code_explorer requires actual code shown or described. If the video just mentions technology names, use info_grid instead.
- Prefer 4 well-populated tabs over 6 tabs where half will be empty.
- When in doubt, use overview or info_grid — they work with any text content.
</rules>
