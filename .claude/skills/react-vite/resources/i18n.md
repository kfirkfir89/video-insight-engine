# Internationalization (React)

react-i18next, translation files, formatting, RTL support, and type-safe translations.

<rules>
- ALWAYS use react-i18next with namespace separation — never hardcode user-facing strings (causes untranslatable UI)
- ALWAYS use `Intl.DateTimeFormat`/`NumberFormat` with the current locale for dates, numbers, and currency — never manual formatting (causes locale-incorrect display)
- ALWAYS use logical CSS properties (margin-inline, padding-block, text-align: start) for RTL support (causes broken layout in RTL languages)
- ALWAYS type translation keys with TypeScript module augmentation for autocomplete and error checking (causes silent missing key errors)
- ALWAYS use `i18next-http-backend` for lazy-loading translation namespaces (causes loading all languages upfront, bloating initial bundle)
- NEVER concatenate translated strings — use interpolation `t('greeting', { name })` (causes broken grammar in other languages)
- NEVER hardcode date/number formats — locale-aware formatting handles all regional differences (causes wrong formats for non-English users)
</rules>

---

## Setup

Configure with fallback language, detection, lazy-loaded backends, and namespace separation.

```typescript
i18n.use(Backend).use(LanguageDetector).use(initReactI18next).init({
  fallbackLng: 'en',
  supportedLngs: ['en', 'es', 'fr', 'de', 'ja'],
  ns: ['common', 'auth', 'errors'],
  defaultNS: 'common',
  backend: { loadPath: '/locales/{{lng}}/{{ns}}.json' },
  detection: { order: ['localStorage', 'navigator'], caches: ['localStorage'] },
});
```

---

## Translation Usage

Use `useTranslation()` hook. Access specific namespaces with `useTranslation('auth')` or `useTranslation(['common', 'dashboard'])`.

```tsx
const { t } = useTranslation();
<h1>{t('app.title')}</h1>
<p>{t('greeting', { name: user.name })}</p>
<p>{t('items.count', { count: cart.length })}</p>  {/* Pluralization */}
```

Use `<Trans>` component for JSX interpolation.

## Type Safety

ALWAYS augment i18next types for autocomplete:

```typescript
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common';
    resources: { common: typeof common; auth: typeof auth; };
  }
}
```

---

## Date & Number Formatting

ALWAYS use Intl APIs with `i18n.language`:

```tsx
const formatDate = (date: Date) => new Intl.DateTimeFormat(i18n.language, { dateStyle: 'long' }).format(date);
const formatCurrency = (amount: number) => new Intl.NumberFormat(i18n.language, { style: 'currency', currency: 'USD' }).format(amount);
```

---

## RTL Support

ALWAYS set `document.documentElement.dir` based on language. Use `ps-`/`pe-`/`ms-`/`me-` Tailwind classes (logical properties).

---

## Edge Cases

- **Lazy namespaces:** Use `useSuspense: false` with `useTranslation('admin')` for on-demand namespace loading in non-critical routes. Show spinner until `ready` is true.
- **Pluralization rules:** Some languages have 3+ plural forms (Arabic, Russian). Always test with count=0, 1, 2, 5, 21 to verify all forms.
- **String length variation:** German/French translations are often 30-50% longer than English. Test UI with the longest supported language to catch overflow.

---

## Rules Summary

All user-facing strings go through react-i18next with namespace separation and lazy-loaded backends. Translation keys are type-safe via module augmentation. Interpolation and pluralization are handled by the t() function, never string concatenation. Dates and numbers use Intl APIs with the current locale. RTL languages get document.dir set automatically and logical CSS properties ensure correct layout. Translation files are lazy-loaded per namespace, and UI is tested with the longest supported language.
